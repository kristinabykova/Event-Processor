# Event Processor

Микросервис, который принимает S2S-запросы от ADs Service и
Payment Service и передаёт объединённые данные в AdVantage.

**Стек:** Python, FastAPI, SQLAlchemy Async, PostgreSQL, asyncpg, httpx, Pydantic, Poetry, Docker, Docker Compose.


Сервис принимает два типа входящих событий:

#### Click event

```json
{
  "clid": str,
  "ad_id": int,
  "click_spend": float,
  "ts": datetime
}
```

#### Payment event

```json
{
  "clid": str,
  "payout": float,
  "ts": datetime
}
```

После получения обеих частей данных сервис формирует payload для AdVantage.
Так как про валюту ничего не сказано, она задана по умолчанию в классе Settings().

```json
{
  "clid": str,
  "payout": float,
  "click_spend": float,
  "click_ts": datetime,
  "payment_ts": datetime,
  "payout_currency": str,
  "click_spend_currency": str
}
```

## Основная логика

В проекте используется одна таблица advantage_outbox. 

Она содержит следующие столбцы

| Поле | Описание |
|---|---|
| id | Первичный ключ записи |
| clid | Идентификатор клика |
| click_spend | Стоимость клика |
| click_ts | Время клика |
| click_spend_currency | Валюта стоимости клика |
| payout | Сумма покупки |
| payment_ts | Время покупки |
| payout_currency | Валюта покупки |
| status | Статус отправки записи |
| created_at | Дата и время создания записи |
| updated_at | Дата и время последнего обновления записи |
| count_retry | Количество попыток повторной отправки |
| next_retry_at | Дата и время следующей попытки отправки |

### Если первой пришла покупка

Создаётся строка с данными покупки:

```text
id = ...
clid = 123
click_spend = NULL
click_ts = NULL
click_spend_currency = NULL
payout = 1800
payment_ts = ...
payout_currency = RUB
status = WAITING_CLICK
created_at = ...
updated_at = ...
count_retry = 0
next_to_retry = NULL
```

Когда позже приходит клик с тем же `clid`, сервис:
* дописывает click-данные **во все ожидающие** покупки с этим `clid`;
* переводит полученные строки в статус `READY_TO_SEND`.

### Если первым пришёл клик

Создаётся строка с данными клика:

```text
id = ...
clid = 1234
click_spend = 1000
click_ts = ...
click_spend_currency = RUB
payout = NULL
payment_ts = NULL
payout_currency = NULL
status = WAITING_PAYMENT
created_at = ...
updated_at = ...
count_retry = 0
next_to_retry = NULL
```

Когда позже приходит **первая** покупка с этим `clid`, сервис:
* дописывает данные покупки в эту строку;
* переводит её в `READY_TO_SEND`.

То есть мы получаем строку вида:

```text
id = ...
clid = 1234
click_spend = 1000
click_ts = ...
click_spend_currency = RUB
payout = 1500
payment_ts = ...
payout_currency = RUB
status = READY_TO_SEND
created_at = ...
updated_at = ...
count_retry = 0
next_to_retry = NULL
```

Если затем приходит **ещё одна новая** покупка с тем же `clid` сервис:

* создаёт новую строку, в которую копируются уже известные click-данные из указанной выше строки;
* у созданной строки статус сразу `READY_TO_SEND`, так как все данные известны.

**Алгоритм можно также изучить с помощью комментариев в коде в файле crud.py**

#### Повторные клики

Если по `clid` уже есть сохранённые click-данные, повторный клик считается артефактом и игнорируется.


#### Повторные покупки


* Если приходит покупка с тем же `clid` и тем же `ts`, она считается дублем и игнорируется.

* Если `clid` тот же, но `ts` другой - это новая покупка, которую нужно отправить в AdVantage.

#### Конкурентная обработка повторных кликов

При высокой нагрузке теоретически возможна ситуация, когда два одинаковых клика с одним `clid` приходят одновременно и оба успевают пройти проверку до записи данных в БД. Такую ситуацию можно дополнительно защитить одним из способов:

* использовать транзакционную блокировку по `clid`;
* добавить отдельный признак первого клика и уникальное ограничение на уровне БД.

### Статусы событий

WAITING_CLICK - покупка ожидает клик

WAITING_PAYMENT - клик ожидает покупку

READY_TO_SEND - событие готово к отправке

SENT - событие успешно отправлено

FAILED - событие не удалось отправить после всех retry, оно отправляется на ручную проверку


## Фоновый poller

Poller запускается вместе с FastAPI через lifespan и работает на фоне.

Алгоритм:

```text
1. Найти события со статусом READY_TO_SEND.
2. Выбрать только те записи, у которых:
   - next_retry_at IS NULL, то есть отправки ещё не было;
   - или next_retry_at <= now, то есть наступило время следующей попытки.
3. Отправить событие в AdVantage через HTTP POST.
4. Если AdVantage вернул 200 — перевести запись в SENT.
5. Если ответ не 200 или произошла ошибка сети, необходимо увеличить счетчки ретраев и назначить следующую попытку.
6. Если все попытки исчерпаны, то перевести запись в FAILED.
```

Каждые 24 часа пуллер запускает просмотр записей со статусом SENT и удаляет отправленные события из БД.

### Retry-логика

Для повторной отправки используется массив задержек:

```python
RETRY_DELAYS = [1, 1, 1, 10, 100, 1000]
```

После каждой неудачной отправки:
* `count_retry += 1` 
* `next_retry_at = now + delay`.


### Email-алерты

Если сервис даже после нескольких ретраев не смог доставить данные, может быть выполнена ручная проверка.

Если событие переходит в статус `FAILED`, сервис отправляет email-алерт.

В письме указываются следующие данные:

```text
id
clid
payment_ts
click_ts
retry_count
status
```

### Логи

Если возникнет ошибка с записью в БД, данные могут быть потеряны. Для этого в программу добавлено логирование.

```python
logger.exception(
    "Failed to save click event to advantage_outbox: clid=%s, ts=%s",
    data.clid,
    data.ts,
  )
```

Оно позволяет зафиксировать ошибки при обработке входящих событий и определить, какие данные не удалось записать в таблицу.

Сервис пишет логи в stdout, поэтому при запуске через Docker их можно смотреть командой:

```bash
docker logs container_name
```

В режиме реального времени:

```bash
docker logs -f container_name
```

## Особенности реализации

Все временные интервалы, включая интервалы повторных попыток отправки и период удаления записей со статусом SENT, выбраны как типовые значения. В реальной системе эти параметры выбираются с учётом бизнес-требований, допустимых задержек доставки и т.д.
